# Benchmarks

## Suites

| Suite | Tasks | Purpose |
|---|---|---|
| `benchmarks/smoke` | 2 | Fast sanity check; always passes with the clean reference agent |
| `benchmarks/coding` | 10 | Varying input size/magnitude (easy/medium/hard by number count) |
| `benchmarks/tool_use` | 5 | Larger input sets, exercising more tool-call sequences |
| `benchmarks/recovery` | 3 | Degenerate inputs (zero, cancelling pairs, large magnitude) |
| `benchmarks/adversarial` | 3 | Tight step budgets (`max_steps=4`) so competence actually matters |
| `benchmarks/failures` | 5 | Deterministic failure-mode demo suite — see below |

23 tasks total, generated by `scripts/generate_benchmark_tasks.py` rather
than hand-written — see that script's docstring and
`docs/research/limitations.md` for why every task is currently the same
underlying operation (sum the numbers in `input.txt`, write the result to
`output.txt`) despite the category labels suggesting broader coverage.
Regenerate with:

```bash
uv run python scripts/generate_benchmark_tasks.py
```

## Task format

Each task is a YAML file (see `arl/domain/task.py` for the schema):

```yaml
id: coding-001
description: "input.txt contains a list of numbers. Compute their sum and write the result to output.txt."
category: coding
difficulty: medium
environment: sandboxed_fs
grader:
  kind: numeric_file_equals
  config:
    path: output.txt
    expected: 12.34
    tolerance: 1.0e-06
timeout_seconds: 10.0
max_steps: 8
metadata:
  initial_files:
    input.txt: "1.1 2.2 9.04"
```

## Graders

Defined in `arl/evaluation/graders.py`:

- `file_equals` — exact string match on a file's content. Use only for
  non-numeric output; using this for floats will produce false failures
  from floating-point summation order (this was a real bug found and
  fixed during development — see `docs/research/experiments.md`'s git
  history if you're curious).
- `numeric_file_equals` — parses a file's content as a float and checks
  it's within `tolerance` of `expected`. Use this for any numeric result.
- `file_contains` — substring match.
- `termination_reason` — checks how the run ended (`agent_finished`,
  `timeout`, `max_steps_exceeded`).

All graders are deterministic. There is no LLM-judge grader in this
system by design (see `docs/evaluation.md`).

## Running a suite

```bash
uv run arl benchmark run benchmarks/coding
uv run arl benchmark run benchmarks/coding --json   # machine-readable
```

## `benchmarks/failures`: deterministic failure-mode demo

Every other suite runs the reference agent clean, so it always succeeds —
useful for proving the pipeline works, useless for demonstrating what the
failure analysis engine (`docs/failure-analysis.md`) actually does.
`benchmarks/failures` exists specifically to show real, non-fabricated
failure diagnoses:

```bash
arl benchmark run benchmarks/failures
```

Five tasks, each engineered to deterministically trigger one specific
detector. "Deterministic" here is verified, not assumed — every task was
run with `--seed 0`, `1`, `42`, and `9999` and produced the identical
category every time (also covered by
`tests/integration/test_failure_benchmark.py::Test*::test_deterministic_across_seeds`).

### How the failure injection works

Two additive mechanisms in `arl.agents.reference`, both opt-in via task
`metadata` and both no-ops for every task that doesn't set them (i.e.
every task outside this suite):

- **`metadata.fault_profile`** — kwargs for the existing `FaultProfile`
  (rate-based, e.g. `repeat_action_rate: 1.0`), applied for the whole run.
- **`metadata.scripted_steps`** — a mapping of `decide()` call index to a
  forced tool call, e.g. `{0: {tool_name: filesystem, arguments: {op:
  read, path: does_not_exist.txt}}}`. Bypasses `FaultProfile` for that one
  call only; every unscripted call still goes through the agent's normal
  plan/fault logic. This is what makes it possible to construct a
  trajectory with an exact, specific shape (e.g. "exactly 3 identical
  failing calls, then normal behavior") rather than relying on
  population-level probabilities.

Both mechanisms produce **real trajectories through the real
runner/tools/agent stack** — the same `run_task()`, the same tool
registry, the same `ToolError` exceptions from real tool code (e.g. a
genuinely missing file, a genuinely missing required argument). Nothing
about the final diagnosis is hard-coded; every number below was captured
by actually running `arl benchmark run benchmarks/failures` and
`arl runs analyze <run_id>`.

### The five scenarios

**1. `looping.yaml`** — `fault_profile.repeat_action_rate: 1.0`. The
agent's first action (list files) succeeds; every decision after that has
probability 1.0 of repeating the previous action instead of progressing,
so it calls `filesystem list` four times identically, then the plan
considers itself complete (4 tool calls recorded) and finishes without
ever writing `output.txt`. Real result:

```
Diagnosis: looping_failure
Confidence: 0.95
Wasted tool calls: 0
Recovered: False
  - 6 events are part of an identical repeated tool call
```

**2. `error_recovery.yaml`** — `scripted_steps` forces call indices 0, 1,
2 to all attempt `filesystem read does_not_exist.txt`, an exact repeat of
a failing call. Index 3+ falls through to the normal plan, which (having
seen 3 tool calls) proceeds to "write", using its default value since no
successful read/calculator result exists — producing a wrong answer, not
a crash. This scenario technically also matches `detect_looping` (3
identical failing reads), but `detect_error_recovery_failure`'s fixed
0.9 weight beats looping's ratio-based weight (`0.75` here — 3 of 4 total
calls are part of a repeat) once evaluated, so this one real trajectory
resolves to a specific, correct category rather than an arbitrary one:

```
Diagnosis: error_recovery_failure
Confidence: 0.95
Wasted tool calls: 3
Recovered: False
  - a tool error was followed by retrying the exact same failing call
```

**3. `timeout.yaml`** — plain `timeout_seconds: 0.0`, no fault injection
needed at all. This exercises the exact `elapsed >= timeout_seconds` path
in `arl/runtime/runner.py` (fixed for cross-platform determinism — see
git history), so the agent never gets a chance to run:

```
Diagnosis: timeout_failure
Confidence: 0.95
Wasted tool calls: 0
Recovered: False
  - run exceeded its timeout budget
```

**4. `tool_misuse.yaml`** — `scripted_steps` forces call index 3 (the
"write" step) to call `filesystem` with no `path` argument, which the
tool itself rejects (`invalid_arguments`). This is a *single, isolated*
error — the agent doesn't retry it and doesn't loop — so
`detect_looping` and `detect_error_recovery_failure` correctly find
nothing, and `detect_tool_selection_failure` (the weakest-weight, most
general detector, at a fixed 0.4) is the only one that fires:

```
Diagnosis: tool_selection_failure
Confidence: 0.70
Wasted tool calls: 1
Recovered: False
  - 1 tool error(s) occurred without a clear retry/loop pattern
```

**5. `partial_recovery.yaml`** — `scripted_steps` forces only call index
0 to read a nonexistent file; every later call is normal plan logic,
which finds the real input and writes the correct answer. The task
**succeeds**. `diagnose()` — by existing design, unchanged here — never
assigns a failure category to a successful run, so:

```
Diagnosis: none
Confidence: 1.00
Wasted tool calls: 0
Recovered: True
```

`FailureDiagnosis.evidence` is intentionally empty for this case — a
successful run isn't diagnosed at all, by design (see
`arl/analysis/engine.py`). The mid-run error is real and visible in the
trajectory (`arl runs inspect <run_id>`, or the committed example at
`docs/examples/failure_report_example.md`), just not in the diagnosis
object, since the diagnosis object only exists to explain failures.

### A pre-existing quirk this suite surfaces

`arl runs inspect`/`arl report generate` show `Run.status` as
`succeeded` for every one of these tasks except the timeout one — even
the ones the grader marked `Success: False`. This is because `Run.status`
is set from `terminated_reason == "agent_finished"`
(`arl/runtime/runner.py`), which only tracks whether the *agent* thinks
it's done, not whether the *grader* agreed. This is a pre-existing
inconsistency, not something introduced by this suite, and is left
as-is here rather than fixed, since changing `RunStatus` semantics is a
larger change than "add a failure-injection benchmark" and would need its
own review of every place that reads `Run.status`.
