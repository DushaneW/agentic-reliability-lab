# Benchmarks

## Suites

| Suite | Tasks | Purpose |
|---|---|---|
| `benchmarks/smoke` | 2 | Fast sanity check; always passes with the clean reference agent |
| `benchmarks/coding` | 10 | Varying input size/magnitude (easy/medium/hard by number count) |
| `benchmarks/tool_use` | 5 | Larger input sets, exercising more tool-call sequences |
| `benchmarks/recovery` | 3 | Degenerate inputs (zero, cancelling pairs, large magnitude) |
| `benchmarks/adversarial` | 3 | Tight step budgets (`max_steps=4`) so competence actually matters |

23 tasks total, generated by `scripts/generate_benchmark_tasks.py` rather
than hand-written — see that script's docstring and
`docs/research/limitations.md` for why every task is currently the same
underlying operation (sum the numbers in `input.txt`, write the result to
`output.txt`) despite the category labels suggesting broader coverage.
Regenerate with:

```bash
uv run python scripts/generate_benchmark_tasks.py
```

## Task format

Each task is a YAML file (see `arl/domain/task.py` for the schema):

```yaml
id: coding-001
description: "input.txt contains a list of numbers. Compute their sum and write the result to output.txt."
category: coding
difficulty: medium
environment: sandboxed_fs
grader:
  kind: numeric_file_equals
  config:
    path: output.txt
    expected: 12.34
    tolerance: 1.0e-06
timeout_seconds: 10.0
max_steps: 8
metadata:
  initial_files:
    input.txt: "1.1 2.2 9.04"
```

## Graders

Defined in `arl/evaluation/graders.py`:

- `file_equals` — exact string match on a file's content. Use only for
  non-numeric output; using this for floats will produce false failures
  from floating-point summation order (this was a real bug found and
  fixed during development — see `docs/research/experiments.md`'s git
  history if you're curious).
- `numeric_file_equals` — parses a file's content as a float and checks
  it's within `tolerance` of `expected`. Use this for any numeric result.
- `file_contains` — substring match.
- `termination_reason` — checks how the run ended (`agent_finished`,
  `timeout`, `max_steps_exceeded`).

All graders are deterministic. There is no LLM-judge grader in this
system by design (see `docs/evaluation.md`).

## Running a suite

```bash
uv run arl benchmark run benchmarks/coding
uv run arl benchmark run benchmarks/coding --json   # machine-readable
```
