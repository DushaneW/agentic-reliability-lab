# Methodology

## Research question

Can features extracted from a *partial* agent trajectory predict whether
the run will ultimately fail — before it finishes?

## Why this is the question, not "can an LLM agent be reliable"

This system does not call a real LLM. There is no API key wired into the
build/test environment this project was developed in (see
`docs/research/limitations.md`), so building a benchmark around live model
calls would mean either faking results or making the whole project
nondeterministic and expensive to reproduce. Instead, the reference agent
(`arl/agents/reference.py`) is a deterministic scripted policy with a
`FaultProfile` that injects controlled, disclosed incompetence: wrong tool
selection, action repetition, ignoring errors, premature termination.

This reframes the research question honestly: **can the detection
pipeline (features → classifier → early-warning signal) find real signal
in trajectory shape, given trajectories with these known failure modes?**
It does not answer whether the same features would predict failure in a
real LLM agent's trajectories — that would require running this same
pipeline against real agent logs, which is exactly what an external-agent
adapter (see `arl/agents/base.py`) is for. That's future work, not
something this repository claims to have done.

## Hypothesis

Failure modes leave a detectable footprint in the shape of a
trajectory — repeated identical actions, tool errors that aren't followed
by adapted behavior, actions concentrated on a shrinking set of tool
calls — and that footprint is present, in weaker form, before the run
actually finishes. If so, a classifier trained on trajectory-prefix
features should show increasing predictive power (AUROC) as more of the
trajectory becomes available.

## Dataset

Generated by `arl/reliability/dataset.py`. For each task in
`benchmarks/coding`, `benchmarks/tool_use`, and `benchmarks/smoke`:

1. Run the reference agent under each of 8 `FaultProfile` configurations
   (from "clean" to "wrong_tool_rate=0.3, repeat_action_rate=0.2,
   ignore_error_rate=0.5, premature_termination_rate=0.1"), 10 seeds per
   profile.
2. Grade the completed run with the task's real deterministic grader
   (`arl/evaluation/graders.py`) to get the ground-truth label.
3. Sample the resulting trajectory at 20%, 40%, 60%, 80%, and 100%
   completion. Each sample is one training example: features extracted
   from that prefix, labeled with the *actual final outcome* of that
   specific run.

This produces roughly 6,600 examples from 17 underlying tasks (see
`docs/research/limitations.md` for why the task suite is currently
narrow). Train/test split is by `run_id` (70/30), not by individual
example, so no example from a given run leaks across the split.

## Features

Defined in `arl/reliability/features.py`, computed purely from the event
log available at that point in the trajectory (nothing looks ahead):

| Feature | What it measures |
|---|---|
| `trajectory_length` | Total events so far |
| `tool_call_count` | Number of tool invocations so far |
| `tool_error_count` | Number of failed tool calls so far |
| `tool_error_rate` | Errors / tool calls |
| `repeated_action_ratio` | Fraction of consecutive tool calls that are identical (name + arguments) |
| `action_diversity` | Distinct (tool, arguments) signatures / tool call count |
| `consecutive_error_pairs` | Back-to-back tool_error events |
| `steps_since_last_error` | Recency of the most recent tool error |
| `distinct_tools_used` | How many different tools have been called |

## Baseline

Logistic regression (`sklearn.linear_model.LogisticRegression`,
`class_weight="balanced"`), not a neural network. At ~6,600 examples and 9
features, model capacity is not the bottleneck — the question is whether
*any* of these hand-built features carry signal, and a linear model is the
right place to check that before reaching for something less
interpretable. See `docs/research/limitations.md` for what would justify
moving past this baseline.

## Metrics

- **AUROC / AUPRC**: threshold-independent measures of ranking quality;
  reported both overall and broken out by trajectory completion fraction,
  since the completion-fraction breakdown is the actual early-warning
  result.
- **Precision / recall / F1** at the default 0.5 probability threshold.
- **False positive rate**: how often a run that actually succeeded gets
  flagged as likely to fail — the cost side of any intervention that acts
  on this prediction.

## Experimental protocol

`arl reliability train` regenerates the dataset with a fixed base seed,
splits by run, trains, evaluates on the held-out split, and writes both
the model (`models/reliability_model.pkl`) and metrics
(`models/reliability_metrics.json`) to disk. Re-running it end to end
reproduces the numbers in `docs/research/experiments.md` exactly — verified
by running `arl reliability train --seeds-per-profile 10` twice in a row
and diffing the resulting metrics files (identical). This required one
fix during development: `arl/reliability/dataset.py` originally let each
`Run` get a random `uuid4()` id, and since the train/test split is done by
`run_id` (not by individual example), a random id meant the split landed
on different runs every execution even with `train_test_split`'s
`random_state` fixed — silently breaking reproducibility despite every
other input being seeded. Run ids are now derived deterministically from
`(task_id, fault_profile, seed)`.
